### `render` 工具的 `captionsBurned` 假診斷（新增 ROADMAP 條目）

Task 7 的實測發現：把 `python3` 移出 `PATH`（保留 ffmpeg／ffprobe）、專案有字幕、
`subtitles: 'burn'` 時，`render()` 是**直接 reject `spawn python3 ENOENT`**，而不是
「回傳成功但 `captionsBurned: false`」。但 `mcp.ts` render handler 的註解與 `note` 三元式
都假設後者。Task 8 把它拆成三塊處理，界線如下：

| 東西                                               | 性質       | 本次處理                                                           |
| -------------------------------------------------- | ---------- | ------------------------------------------------------------------ |
| 那段 `// burn 模式下沒燒成功才值得警告…` 的註解    | 純文件     | **已改**（授權例外 2），改成下面查證出來的正確描述                 |
| `note` 三元式裡的 `'is python3/Pillow available?'` | 執行期輸出 | **未動**，動它算行為變更 → 已記進 `docs/ROADMAP.md` 第 11 條待裁決 |
| `captionsBurned: false` 這條分支到底可不可達       | 需要判定   | **判定為可達，但成因不是它說的那個**（見下）                       |

**判定過程（只讀程式碼，未跑 render）**：

1. `server/src/render.ts` 的 `render()` 只在 `captions.length > 0 && subtitleMode === 'burn'`
   時才填 `captionCards`，否則維持 `[]`。
2. `renderCaptionCards()` 對每條 caption **至少**回一張卡：沒有 `tokens`（或 `tokens` 是
   空陣列）回 1 張，有 `tokens` 回 `tokens.length` 張。所以 `captionCards.length === 0`
   ⟺ `captions.length === 0`。
3. `buildRenderArgs()` 的 `useCards = burnCaptions && captionCards.length > 0`，
   `captionsBurned` 只在 `useCards` 為真時被設成 `true`。

⇒ **burn 模式下 `captionsBurned === false` ⟺ 專案的字幕軌是空的。** 這條分支**不是死碼**，
但唯一可達的情境，跟 `note` 告訴使用者的成因完全無關。

而 `note` 點名的兩個成因都走不到這裡：python3 不在 → `renderCaptionCard()` 的
`spawn('python3', …)` 丟 ENOENT；字型候選鏈全滅 → `text_card.py` 的 `load_font` 回
fallback、被 `fontFallbackError()` 轉成 reject。**兩者都經 `render.ts` 的 `mapLimit`
（任一項 reject 就整體 reject）讓整個 `render()` 失敗**，落到 handler 的 catch 回
`render failed: …`。也就是說：ROADMAP 移交時問的「這個分支存不存在」——存在，
但它是個**假診斷**，不是死碼。

**⚠️ 措辭要精確：能讓 render 失敗的是「`text_card.py` 的候選鏈全滅」，不是「server 的
字型表是空的」。這兩件事不一樣，Task 7 傳下來的「字型表是空的」措辭把它們混同了。**

- **`text_card.py` 的候選鏈全滅**（`FONT_CANDIDATES` 一條都開不了）→ `load_font()` 回
  `fallback=True` → `renderCaptionCard()` 的 `child.on('close')` 裡

- **server 的 `fonts.ts` 表空** → `captionFontResolver()` 回 `undefined` → payload 的
  `fontPath` 是 `null` → `load_font_by()` 退回 `load_font()`，也就是**改用 python 自己
  那份清單**。而 `FONT_CANDIDATES` 是 `fonts.ts` 的 `CANDIDATES` 的**嚴格超集** ——
  本次逐條比對（14 條 vs 11 條，`CANDIDATES` 沒有任何一條是 py 缺的），py 多出這三條：
  `/System/Library/Fonts/Supplemental/Arial.ttf`、

  所以在一台只有 `Arial.ttf` 開得了的機器上：server 表空、python 照樣用 Arial 產出字卡、
  `captionsBurned: true`、**render 正常成功**。
  ⇒ **「server 字型表空」推不出「render 失敗」。**

本次修正的就是這一步：稽核第一版沿用了「字型表是空的」這個較弱的前提，卻下了「同樣是

措辭本來就是對的，不受這條修正影響。**

「候選鏈全滅」這條**仍然沒有實測**（要實測得先做出一台 `FONT_CANDIDATES` 14 條全開不了
的機器），如實標明是讀碼判定。要低成本逼出這條路徑的話：讓 `fontPath` 指向一個不存在的

### 1. `server/test/mcp-docs-sync.test.ts`（6 條測試，跟著 `npm test` 跑）

**守什麼**：`CLAUDE.md` 鐵則第三步的執行面 ——「`shared/src/types.ts` 加了 `Command`
variant、`commands.ts` 加了 case，卻忘記在 `mcp.ts` `registerTool`」。前一、二步漏掉會被
`tsc` 抓到（switch 少 case 編不過），**只有第三步從前沒有任何東西擋**（前例：`addClip`
做完八輪 TDD 卻沒人能用）。取代的舊守衛硬編 6 個工具名做 `toContain`，工具真的沒註冊時
照樣綠。

**失效時會看到什麼**（訊息是逐字從測試檔抄的）：

```
這些 Command variant 沒有對應的 MCP 工具，也沒列進豁免表：<variant>
＝ AI 永遠碰不到這個能力（CLAUDE.md 鐵則第三步）。

這些工具既沒寫進 instructions、也沒列進 INSTRUCTIONS_EXEMPT：<tool>
AI 使用者只能靠 instructions 認識工具面——要嘛把它寫進去，要嘛在豁免表裡寫下理由。

instructions 提到但實際沒註冊的工具：<tool>
```

**怎麼修**：

- 第 1 條紅 → 去 `mcp.ts` 補 `registerTool`。若那個 variant 是刻意由別的工具間接觸達
  （像 `splitAt` 由 `timeline_op` 的 `op:"split"`），才把它加進 `MCP_EXEMPT_COMMANDS`
  **並寫下理由**（那個 map 的 value 就是理由字串）。
- 第 2 條紅 → 把工具寫進 `mcp.ts` 的 `instructions`，或加進 `INSTRUCTIONS_EXEMPT` 附理由
  （既有的四個豁免是 `get_project`／`get_history`／`undo`／`redo`：唯讀查詢或通用復原，
  描述已自足）。
- 第 3 條紅（反方向）→ instructions 裡還留著已經移除的工具名，刪掉那段描述。
- 第 4／5 條紅 → 豁免清單自己過期了，刪掉不存在的那幾筆。

⚠️ 第 3 條是用「instructions 裡形如 snake_case 且長度 ≥ 4 的詞」當工具名候選。**在

### 2. `node scripts/docs-check.mjs`（秒級，gauntlet 的「文件引用」關卡）

**守什麼**：斷言型文件（`DOCS` 常數列的 6 份）不得指向不存在或被 `.gitignore` 的東西。
只驗三件能百分之百判定的事：`npm run X` 的 X 真的存在（會查對應 workspace 的
`package.json`）、反引號裡形如 `path/to/file.ext` 的路徑真的存在、沒有引用被忽略的路徑
（`.superpowers/`、`projects/`、`node_modules/`、`dist/`、`coverage/` 開頭且以副檔名結尾）。

**綠的時候**：`文件引用檢查：6 份斷言型文件的引用都指向真實存在的東西`

**紅的時候**：先印 `文件引用檢查：N 個問題`，然後每行一條，四種形狀：

```
<doc>: 這份文件本身不存在（DOCS 清單過期）
<doc>: `npm run <name>` —— <dir>/package.json 裡沒有這個 script
<doc>: 引用了不存在的檔案 `<path>`
<doc>: 引用了被 .gitignore 的路徑（`<path>`）——別人 clone 之後必然失效
```

**怎麼修**：前三種通常是文件過期（檔案改名／script 改名／文件寫錯路徑），改文件。
第四種是文件引用了 clone 後不存在的東西，改成引用一個進 git 的檔案，或整段改寫成不指向
具體檔案。**零誤報是這支的硬要求**：如果你確信文件沒錯是檢查器錯了，改檢查器並在
`docs/DOC-AUDIT-*.md` 記一筆——但先確認不是自己寫了字面量的 `npm run X`（Task 5 踩過：
文件裡舉例用的假 script 名被當成真的，最後是改措辭而不是放寬檢查器）。

### 3. `node scripts/mutate.mjs --check`（秒級，`--fast` 也會跑）

**守什麼**：`scripts/mutants.json` 每一隻的 `find` 字串在目標檔**恰好出現一次**。
存在理由：`find` 字串會被正當重構打斷，而突變引擎找不到就靜默不跑那隻——曾經一次五隻
同時失效無人察覺（`render-aspect`／`mcp-writereply-always-err`／`setaudio-validate`／
`tl-anchor-offset`／`inspector-deselect`）。這支不跑任何測試，所以是秒級的。

**綠的時候**：`<N>/<N> mutants 的 find 字串都在目標檔恰好命中一次`

**紅的時候**：

```
ERROR: <mutant id> — find 出現 <N> 次（需恰好 1 次）
```

**怎麼修**：去 `scripts/mutants.json` 把那隻的 `find`（多半連同 `replace`）更新成重構後
的樣子。出現 0 次＝程式碼被改寫了；出現 2 次以上＝那段字串已經不唯一，把 `find` 加長到
唯一為止（既有做法：以整個迴圈區塊當 `find`，見 `import-serial`）。**更新完務必跑一次
完整的 `node scripts/mutate.mjs <id>` 確認它真的還殺得掉**——`--check` 只證明錨點還在，
不證明那隻仍有殺傷力。
